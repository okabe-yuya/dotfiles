# oil スキル — 仕上げ（オイルフィニッシュ）

未コミットのコードを「多重レビュー → 修正 → テスト網羅 → commit → PR」まで磨き上げる **オーケストレーション** スキル。木工のオイルフィニッシュのように、何度も塗り重ねて（レビューを重ねて）表面を仕上げるイメージ。

各ステップは既存スキル（`/my-review` / `/git-cp` / `/git-pr`）と専用エージェント（**Fable5 レビュー** / **qa-reviewer**）を順に呼ぶだけで、本スキル本体に固有のロジックはほぼ持たない。

## 引数

- `[ベースブランチ]`（省略可）: `/git-pr` に渡す base。省略時は `/git-pr` 側の推定に任せる
- `--max-rounds N`（省略可）: レビュー→修正ループの上限。省略時 `3`

---

## 絶対ルール 1: スキル指定のあるステップは必ず `Skill` ツールで呼ぶ

oil は **オーケストレータ** であり、ロジックは各サブスキル／エージェントに閉じている。本スキルが独自判断でそれらの処理を **Bash / Edit / Write / 目視で代替してはならない。**

### 禁止事項

- `Skill: my-review` の代わりに `git diff` + 目視でレビューを済ます
- `Skill: git-cp` の代わりに `git add` / `git commit` / `git push` を直接実行する
- `Skill: git-pr` の代わりに `gh pr create` を直接実行する
- Fable5 レビューを「自分（メインの Opus）で代わりに見た」で済ます（**別モデルの独立した目**が要件。自分では代替不可）
- qa の網羅性確認を `qa-reviewer` エージェントを介さず自分の判断で済ます
- 「小さい変更だから」「さっき見たから」を理由にサブスキル／エージェントを skip する

### なぜ必須か

- 各サブスキルには独自の観点・安全装置・命名/メッセージ規約がある。bypass すると統一性が崩れ、期待する観点が抜ける
- Fable5 レビューと qa-reviewer は **メインとは別の主体**であることに価値がある（同一モデルの自己レビューでは見落としが相関する）。代替すると多重レビューの意味が消える

## 実行フロー

### Step 0: 前提確認

以下を並列で実行する:

```bash
git rev-parse --is-inside-work-tree
git branch --show-current
git status --porcelain
```

**中断条件**:
- git リポジトリ外 → 「git リポジトリ内で実行してください」と報告して終了
- `main` / `master` ブランチ上 → 「base ブランチ上では実行しないでください」と報告して終了
- **未コミット変更なし**（`git status --porcelain` が空） → 「oil はコミットされていない変更を仕上げるスキルです。対象がありません」と報告して終了

### Step 1: ダブルレビュー → 修正ループ（指摘ゼロまで）

`Round` を 1 から数え、`--max-rounds`（既定 3）まで以下を繰り返す。

#### 1-a. `/my-review`（未コミット対象・報告のみ）

バナーを出してから:

```
Skill: my-review
（引数なし = 未コミットの working tree を対象。「報告のみ（修正・確認は oil 側で行う）」として呼ぶ）
```

`/my-review` は Step 4 の指摘列挙まで（Step 5-6 の修正適用・ユーザー確認はスキップ）返す。CRITICAL / HIGH / MEDIUM の指摘を受け取る。

#### 1-b. Fable5 の独立レビュー

バナーを出してから、**`Agent` ツールで `model: "fable"`**・`subagent_type: "code-reviewer"` を指定して起動する。同一ラウンドの 1-a と **並行**でよい。

- プロンプト要点:
  - 対象は **未コミットの working tree 変更**（`git status --porcelain` / `git diff HEAD` / 未追跡ファイル）。ブランチ全体ではなく変更分に集中
  - 観点は `/my-review` のチェックリスト（`~/dotfiles/claude/skills/my-review/SKILL.md` の Step 3）を独立に適用。加えて対象リポの `CLAUDE.md` / `AGENTS.md` / `.claude/rules/*.md` を読んでプロジェクト固有ルールも見る
  - **ファイルは編集しない。** 指摘の列挙のみ（`[CRITICAL|HIGH|MEDIUM] タイトル / File:line / Issue / Fix` 形式）を返す
- Fable5 は「メインとは別モデルの独立した第二の目」。同一観点でもメインが見落とした所を拾うのが狙い

#### 1-c. 指摘の統合と判定

- 1-a と 1-b の指摘を **重複統合（同一 File:line・同一趣旨は 1 件に）** する
- **exit 条件**: 両レビューとも **CRITICAL / HIGH が 0 件**、かつ MEDIUM が「解消済み or 明示的に許容」なら **ループを抜けて Step 2 へ**
- そうでなければ 1-d へ

#### 1-d. 修正の適用

- **CRITICAL / HIGH は必ず修正**する（oil が Edit / Write で適用。誤検知と判断した項目のみ、理由を添えてスキップ可）
- **MEDIUM** は「要確認」でなく明確な改善なら修正。判断が割れるものは 1 メッセージにまとめて `AskUserQuestion` で確認
- 修正で**コードに触れたら、対象リポの流儀で型チェック / lint / テストを回す**（まず `make help` を確認。Henry なら Makefile 集約）。壊れていれば同ラウンド内で直す
- 修正後、`Round` を +1 して **1-a に戻る**（再レビュー）

#### ループ上限に達したら

`--max-rounds` 回まわしても CRITICAL / HIGH が残る場合は、残指摘を提示して `AskUserQuestion`:

> 「{N} ラウンド回しましたが指摘が残っています。どうしますか？」
> - さらに続ける（+N ラウンド） / このまま Step 2 へ進む / 中断する

### Step 2: qa-reviewer でテスト網羅性を確認 → 不足分を追加

レビュー指摘がゼロになったら、バナーを出してから **`Agent` ツールで `subagent_type: "qa-reviewer"`** を起動する。

- プロンプト要点:
  - 対象は今回の未コミット変更（`git diff HEAD` + 未追跡ファイル）で追加・変更されたロジック
  - 不足しているテストケース（分岐・境界値・異常系）を具体的に列挙してもらう
- 返ってきた不足に対し **oil がテストを追加**する（`qa-reviewer` は read-only なので実装は oil が行う）
  - 追加後、対象リポの流儀でテストを実行し **green を確認**する
- テストを追加したら **もう一度 qa-reviewer** を呼び、「網羅性 OK」を確認する（最大 2 巡。なお残る場合は残不足を提示してユーザー判断）
- 「変更にロジックが無くテスト不要」と qa-reviewer が判断した場合はスキップしてよい（その旨を明記）

### Step 3: `/git-cp` で commit & push

Step 1・2 をパスしたら、バナーを出してから:

```
Skill: git-cp
```

`/git-cp` 側で論理単位の分割・コミットメッセージ生成・push まで完結する。

**例外処理**:
- 「コミット対象なし」と返ってきた場合 → Step 4 へ（push 済み state とみなす）
- push 失敗（non-fast-forward 等） → 報告して終了

### Step 4: PR 確認 → 未作成なら `/git-pr`

現ブランチに紐づく PR の有無を確認する:

```bash
gh pr view --json number,state,url --jq '"\(.number) \(.state) \(.url)"' 2>/dev/null
```

- **PR 既存（state=OPEN）**: 作成不要。URL を控えて Step 5 へ
- **PR なし / CLOSED**: バナーを出してから:

```
Skill: git-pr
args: <ベースブランチ>   # oil の引数で渡された場合のみ。無ければ引数なしで /git-pr の推定に任せる
```

### Step 5: 最終レポート

```
✅ oil 完了

- ブランチ: {現ブランチ}
- レビュー: {Round 数} ラウンドで指摘ゼロ化
- 追加テスト: {n} 件（qa-reviewer 指摘に対応 / 不要と判断）
- コミット: {n} 件 push 済み
- PR: {既存流用 / 新規作成} {PR URL}

── 使用したスキル / エージェント（証跡）──
✅ Skill: my-review        × {回数}
✅ Agent: Fable5(code-reviewer, model=fable) × {回数}
✅ Agent: qa-reviewer      × {回数}
✅ Skill: git-cp           × {回数}
✅ Skill: git-pr           × {0 or 1}（既存 PR ありなら 0）
```

## 落とし穴

- **Fable5 を自分で代替しない**: `Agent(model="fable")` を必ず呼ぶ。メイン（Opus）の自己レビューは 1-a の `/my-review` で既に済んでおり、1-b は **別モデルの独立レビュー**であることに意味がある。ここを省くと「ダブルレビュー」が成立しない
- **無限ループ防止**: レビュー→修正は `--max-rounds`（既定 3）で必ず打ち切る。qa 巡回も最大 2 巡。上限到達時はユーザー判断に委ねる
- **exit 条件の揺らぎ**: 「指摘ゼロ」の基準は **CRITICAL / HIGH が両レビューとも 0**。MEDIUM の「要確認」は永遠に消えないことがあるので exit をブロックしない（許容 or 修正を都度判断）
- **report-only の徹底**: 1-a の `/my-review` はオーケストレータ呼び出しなので **報告のみ**（my-review 内で修正・ユーザー確認をさせない）。修正は必ず oil が統括して 1-d で行う（二重修正・修正衝突の防止）
- **テスト実行は変更リポの流儀で**: 型/lint/test コマンドを勝手に決めず、まず `make help` / `CLAUDE.md` / `AGENTS.md` を見る（Henry は Makefile 集約）
- **状態はファイルに持たない**: PR 番号・ブランチ名は `gh pr view` / `git branch --show-current` で都度取り直す。harness 再起動で context が失われても復元可能にする
- **未コミットが前提**: oil は working tree の未コミット変更を仕上げる。既にすべて commit 済みなら対象がないので、その場合は `/git-pr` 等を直接使う

---

## このスキルが向かない用途

- **本番障害調査 / hotfix**: `/prod-investigate`・`/git-hotfix` を直接使う
- **実装そのもの**: oil は「書き上がった未コミット変更の仕上げ」向け。実装計画・実装は `/plan` や実装ターンで
- **CI 緑化まで含めたい**: oil は PR 作成までで終わる。CI 待ち→fail 時 fix ループが要るなら `/dev-cycle`（`/ci-watch` 内包）を使う
- **PR レビューの指摘対応**: 既存 PR への差分対応は個別スキルを直接呼ぶ

## 既存スキルとの境界

| 呼ぶもの | 責務 | oil での扱い |
|--------|------|---|
| `Skill: my-review` | 自分の観点で未コミット変更をレビュー（報告のみ） | Step 1-a で毎ラウンド呼ぶ |
| `Agent(model=fable, code-reviewer)` | 別モデルの独立レビュー | Step 1-b で毎ラウンド呼ぶ |
| `Agent(qa-reviewer)` | テスト網羅性の検証 | Step 2 で呼ぶ（不足あれば oil がテスト追加後に再確認） |
| `Skill: git-cp` | commit + push | Step 3 で呼ぶ |
| `Skill: git-pr` | PR 作成 | Step 4 で PR 未作成時のみ呼ぶ |

oil は **これらを順に呼ぶオーケストレータ**であり、固有ロジックは「ダブルレビュー統合と指摘ゼロ化ループ（上限あり）」「qa 不足のテスト追加」「スキル使用の明示」のみ。
