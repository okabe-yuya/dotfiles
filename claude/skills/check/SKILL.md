# /check — 動作確認チェックリストを作る

変更内容（PR / ブランチ / 未コミット差分 / 仕様）から、**人が手で動作確認するためのインタラクティブな
チェックリスト（HTML）** を生成するスキル。自動テストで担保済みの項目と実機で目視が要る項目を区別し、
進捗バー・チェック状態の自動保存（localStorage）つきで Artifact として公開する。

「動作確認したい」「確認項目をチェックリストにして」「QA チェックリスト作って」と言われたらこれを使う。

## 引数

省略可。対象の指定に使う:

- **PR 番号**（例 `14137`）: `gh pr diff <番号>` / `gh pr view <番号>` を対象にする
- **ブランチ名**: そのブランチの `<base>...HEAD` を対象にする
- **Notion / Linear の URL**: 仕様ドキュメントを対象にする（実装差分と併用可）
- **未指定**: 現在の未コミット変更（`git diff HEAD` + 未追跡）＋直近の作業文脈を対象にする

複数リポにまたがる worktree では、対象リポのパスを引数で明示してよい（`git -C <path>` で扱う）。

---

## 実行手順

### Step 1: 対象の特定と変更内容の把握

1. 引数から対象を決める（上記）。cwd と対象リポが違う場合は `git -C <repo>` / `gh ... -R <owner/repo>` を使う
2. 変更を取得する:
   - PR 番号: `gh pr diff <n>` + `gh pr view <n> --json title,body,files`
   - ブランチ: `git diff <base>...HEAD`
   - 未コミット: `git diff HEAD` + `git ls-files --others --exclude-standard`
   - 仕様 URL: Notion / Linear を fetch（**製品仕様は Notion（設計仕様・受入基準）と Linear（課題・決定経緯）を根拠にする**）
3. **変更ファイルは差分だけでなくファイル全体・呼び出し元も読み**、「ユーザーに見える挙動」を抽出する:
   UI の増減・入力バリデーション・計算結果・表示条件・エラーメッセージ・初期値・状態遷移・印刷/PDF・一覧の並び等

### Step 2: 確認項目の導出

観点ごとにセクション化する。各項目は **「ユーザー操作 → 期待結果」を 1 文** で書く。

- **機能セクション**: 変更した各機能・仕様ごと（正常系）。仕様ドキュメントの受入基準があればそれに沿う
- **境界・異常系**: 入力上限ちょうど/超過・必須/空値・エラーメッセージ文言・重複・権限など
- **回帰確認**: 触った周辺の既存挙動が壊れていないか（最後に 1 セクション）
- 各項目にバッジを付ける:
  - `テスト済み`: unit / component / 結合テストで担保済み（＝実機での回帰確認は軽めでよい）。**実際にそのテストが存在する項目にだけ付ける**
  - `要目視`: 自動テストがない、または実機でしか確認できない（描画・ツールチップ文言・レイアウト・PDF/印刷・保存→再表示の往復・E2E 的挙動）
- `note`（補足）に、手順・確認すべき文言・スキップ条件・`file:line` を書く

### Step 3: HTML を生成（テンプレートを埋める）

同梱テンプレート `templates/checklist.html` をベースに内容を差し替える。テンプレートは
style（白基調＋ダーク対応）・進捗バー・凡例・localStorage 保存スクリプトを含み、**差し替えるのは
コンテンツだけ**。

差し替え箇所:

- `<title>` … 「<機能> 動作確認」の短い名前
- `<meta name="description">` … 1 文の説明（PR 番号など）
- `.eyebrow` / `h1` / `.sub` … 見出しと対象（PR/ブランチへのリンク）
- `.legend` … 使うバッジだけ残す（`テスト済み` が無い変更なら `要目視` の 1 行に減らす）
- 各 `<section>` … `sec-num`（連番）＋ `h2`（観点名）＋ `.card` 内の `.item` 群
- `footer` … 補足（テスト済みの担保範囲・チェックは自動保存される旨）

item のマークアップ（テンプレートの 1 行 `<label class="item">…</label>` を踏襲）:

```html
<label class="item"><input type="checkbox" /><span class="box"><svg viewBox="0 0 14 14"><polyline points="2,7.5 6,11 12,3.5"/></svg></span><span class="body"><span class="text">操作して<b>期待結果</b>になる<span class="badge tested">テスト済み</span></span><span class="note">補足・手順・スキップ条件</span></span></label>
```

- 強調は `<b>`、補足は `<span class="note">`（`code` 可）、バッジは `<span class="badge tested">` / `<span class="badge manual">`

テンプレートには **「Markdown をコピー」ボタン**（GFM タスクリスト形式で出力。チェック状態を `[x]`/`[ ]`、
バッジを `(テスト済み)` 等の接尾辞、note をサブ箇条書きに変換）が組み込み済みで、差し替え不要。
ただし script 内の `KEY`（localStorage のキー）はチェックリストごとに一意な値へ変えること（別の
チェックリストと保存が混ざらないように）。

### Step 4: 公開

原則 **Artifact として公開**する（別デバイスでも開け、チェック状態はビューアのブラウザに保存される）。

- ファイルを書く前に **`artifact-design` スキルを load**（プラットフォームのルール）。ただし本テンプレートは
  設計済みなので、calibration を確認したらそのまま流用してよい
- `Artifact` ツールで publish。`favicon` は `✅`、`title` は「<機能> 動作確認」
- ローカルに保存したい・オフラインで渡したい場合は scratchpad（または `<workspace_root>/.claude-doc/<repo>/`）に
  書き出し、`SendUserFile` で渡すかブラウザで開く

## 方針

- 項目は「**読んだら手が動く**」具体度にする。曖昧語（「適切に」「正しく」「問題なく」）を使わない
- `テスト済み` / `要目視` の判定は **実際のテストの有無に基づく**。憶測で `テスト済み` にしない
- **PII を含めない**（患者氏名・生年月日・患者番号・自由記述等）。医療機関名は OK。組織のルールに従う
- 多すぎる項目は疲れる。**1 セクション 3〜7 項目**を目安に、意味のある回帰に絞る
- 変更が UI に一切現れない（内部リファクタ等）なら、その旨を伝えて「動作確認は不要／自動テストで十分」と提案する

## 同梱ファイル
